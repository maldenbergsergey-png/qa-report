# QA Report

QA Report - web-инструмент для создания, ведения и публикации QA-чек-листов.
Он помогает быстро собрать проверочный отчёт, импортировать таблицы из Jira,
добавить фактические результаты, скриншоты, файлы и код, а затем отправить
готовый отчёт обратно в Jira или сохранить его в истории.

README описывает текущее состояние проекта. Если меняется сценарий, API,
настройка, ограничение или способ запуска, этот файл нужно обновлять в том же
изменении.

## Для Чего Нужен

QA Report закрывает несколько ежедневных QA-сценариев:

| Сценарий | Что делает инструмент |
| --- | --- |
| Создать чек-лист с нуля | Даёт табличный редактор с разделами, колонками, статусами и автосохранением |
| Перенести чек-лист из Jira | Импортирует Jira Wiki Markup или комментарий Jira в редактируемую таблицу |
| Принять чек-лист из QA Assistant | Принимает Jira-разметку через API и возвращает ссылку `/report/<id>?importToken=...` |
| Заполнить отчёт по тестированию | Позволяет вести ожидаемый/фактический результат, статусы, комментарии, вложения и код |
| Опубликовать результат | Отправляет комментарий и вложения в Jira Data Center / Server или Jira Cloud |
| Сохранить варианты отчётов | Ведёт локальную историю с комментариями и короткими публичными ID; облачную историю можно включить в настройках |
| Работать с конфликтами | При включённом облаке показывает различия локальной и облачной версии и не перезаписывает данные без выбора пользователя |

## Пользовательские Возможности

### Редактор чек-листов

- Несколько разделов в одном отчёте.
- Добавление, удаление, дублирование и перемещение строк.
- Создание нового раздела из выбранной строки.
- Пользовательские колонки в каждом разделе.
- Переименование, перемещение и изменение ширины колонок.
- Стабильные `sectionId`, `rowId`, `columnId` для сохранения и сравнения версий.
- Служебные колонки с номером строки и статусом.
- Автоматическая сводка по статусам.

### Нумерация пунктов

В шестерёнке хедера раздел «Чек-лист» открывается первым. Режим нумерации
сохраняется кнопкой «Сохранить настройки» отдельно для текущего отчёта:
с 1 в каждом разделе (по умолчанию), сквозная или «раздел.пункт» (1.1, 1.2, 2.1).
Закрытие окна без сохранения не меняет режим. Номера пересчитываются по порядку
разделов и строк, включая свёрнутые разделы и пустые строки редактора.
Редактор, предпросмотр, Jira-разметка, ADF и Excel используют общий расчёт.
При пропуске пустых строк и отправке отдельных разделов сохраняются исходные номера.
Параметр `numberingMode` хранится в документе и поддерживает историю и отмену.

### Закрепление столбцов

В «Настройки → Чек-лист → Закрепление столбцов» доступны независимые
переключатели номера слева и статуса справа. «Сохранить настройки» применяет
выбор ко всем чек-листам текущего браузера, включая новые; выбор сохраняется
после перезагрузки и синхронизируется между открытыми вкладками.
По умолчанию оба переключателя выключены. Закрытие без сохранения не меняет выбор.
Заголовки и ячейки закрепляются вместе. В режиме выделения чекбоксы остаются
слева от закреплённого номера. Меню действий строки всегда закреплено у правого края
в узкой колонке. При закреплении статуса он располагается слева от меню.
Настройка хранится в `qa-report-pinned-columns-v1` в localStorage, отдельно
от документов, и не меняет порядок столбцов в экспорте.

### Массовое выделение строк

Кнопка с чекбоксом слева на панели форматирования включает режим выделения.
Под ней появляется отдельная панель, которая закрепляется при прокрутке вместе
с текстовой панелью. Слева в каждой таблице появляются чекбоксы строк и раздела;
частичное выделение раздела отображается промежуточным состоянием чекбокса.

- «Выбрать всё» выделяет или снимает выделение со всех строк, включая свёрнутые разделы.
- Выбранные строки подсвечиваются целиком, включая номер и статус, отдельным
  оттенком для светлой, тёмной и графитовой тем.
- Счётчик показывает количество выбранных строк, в том числе пустых.
- «По статусу» позволяет выбрать несколько действующих статусов. Изначально все статусы выключены. «Применить» заменяет текущее выделение строками с этими статусами
  во всём отчёте; без отмеченных статусов выделение снимается.
- «Перенести в раздел» ищет существующие разделы по названию. Можно ввести название
  нового раздела; он создаётся внизу при подтверждении переноса. «Отмена» не меняет
  данные и сохраняет выделение. Форму создания можно раскрыть и свернуть повторным
  нажатием «Создать новый раздел»; введённое название при этом сохраняется. Меню
  остаётся открытым при выделении текста мышью. Прокручивается только список
  разделов с маркерами, а поиск и форма остаются видимыми. Прокрутка списка
  сохраняет позицию при пересчёте размеров меню и не прокручивает страницу. Уже находящиеся в целевом разделе строки остаются
  на месте, остальные добавляются в конец в порядке исходных разделов и строк.
- Перенос сохраняет статусы, форматирование и вложения. Столбцы объединяются по
  названию (с приоритетом совпадающего ID); отсутствующие добавляются в целевой раздел без потери данных.
- «Удалить» после подтверждения удаляет выбранные строки независимо от их порядка.
  Опустевшие разделы сохраняют одну пустую строку. Если удалены все строки отчёта,
  остаётся один раздел «Основные проверки» с двумя пустыми строками и стандартными
  столбцами. Реквизиты и вводный текст отчёта сохраняются.
- Перенос и удаление можно отменить/повторить кнопками истории редактирования.
- Выход из режима скрывает панель и колонку чекбоксов и сбрасывает выделение.
  Выделение не записывается в отчёт и не попадает в экспорт.

### Статусы проверок

Поддерживаются:

- `OK`
- `НЕ ОК`
- `ПОЧТИ ОК`
- `НЕ ПРОВЕРЕНО`
- `ЧАСТИЧНО ПРОВЕРЕНО`
- `ТРЕБУЕТ УТОЧНЕНИЯ`

Сводка пересчитывается сразу после синхронизации текущих значений таблицы, в том
числе при повторных изменениях после автосохранения. Строка с явно выбранным
статусом (кроме «НЕ ПРОВЕРЕНО») учитывается даже без текста. Полностью пустые строки
со статусом «НЕ ПРОВЕРЕНО» не учитываются в итоговой статистике.

### Текст, код, изображения и файлы

- Форматированный вводный текст.
- Жирный, курсив, подчёркивание, зачёркивание, списки, ссылки и цвет текста.
- Кодовые блоки в ячейках и вводном тексте.
- Полноэкранное редактирование кода.
- Копирование кода с Jira-обёрткой `{code}...{code}`.
- Вставка изображений из файлов и буфера обмена.
- Просмотр изображений в увеличенном виде.
- Перетаскивание изображений и кодовых блоков между ячейками.
- Вставка файлов-карточек.

### Импорт и экспорт

- Импорт Jira Wiki Markup вручную.
- Импорт по ссылке на Jira-комментарий.
- Импорт из QA Assistant через API.
- Копирование отчёта как Jira Wiki Markup.
- Копирование визуальной таблицы.
- Предпросмотр Jira-разметки и визуального результата.
- Редактирование Jira-разметки в preview и применение обратно в таблицу.
- Экспорт в XLSX.

### Jira

- Проверка подключения к Jira.
- Публикация отчёта как комментария.
- Поддержка Jira Data Center / Server через Jira Wiki Markup.
- Поддержка Jira Cloud через Atlassian Document Format.
- Загрузка вложений в Jira.
- Диагностика нестандартных ответов Jira, WAF и browser challenge.

### История и версии

- Автосохранение текущего чек-листа.
- Полное локальное хранение в браузере по умолчанию.
- Опциональная серверная история в SQLite, включается во вкладке "Настройки -> История".
- Короткий публичный ID экземпляра, например `851a9bd2`.
- URL текущего чек-листа: `/report/<publicId>`.
- Модалка истории с поиском, источником версии, public ID и комментарием.
- Отдельный пользовательский комментарий для каждого экземпляра отчёта.
- Удаление локальных и серверных записей из истории.
- Очистка истории текущего пространства.

### Конфликты версий

- Обнаружение отличий между локальной и облачной версией.
- Облачные конфликты и синхронизация работают только если включён флаг "Сохранять чек-листы в облачном хранилище".
- Сравнение по содержимому, а не по служебным полям вроде `updatedAt` или `revision`.
- Diff по стабильным ID разделов, строк и колонок.
- Подсветка новых строк, колонок, разделов и изменённых ячеек.
- Защита от перезаписи пользовательских названий колонок дефолтным или пустым значением.
- Выбор облачной версии.
- Явная перезапись облака локальной версией.
- Сохранение обеих версий: облачная остаётся на старом `publicId`, локальная расходящаяся версия создаётся как новая копия с новым `publicId`.

## Быстрый Запуск

Локально:

```bash
npm start
```

Откройте:

```text
http://localhost:4173
```

Эквивалентный запуск без npm:

```bash
node server.js
```

Простое открытие `index.html` подходит только для автономного редактирования.
Jira, feedback, загрузка вложений, серверная история, входящий импорт и healthcheck
требуют запущенный `server.js`.

## Основные Сценарии

### Создать чек-лист

1. Откройте приложение.
2. Заполните ссылку на Jira-задачу, окружение и итоговый статус.
3. Добавьте разделы, строки и колонки.
4. Заполните проверки, ожидаемый и фактический результат.
5. При необходимости добавьте изображения, файлы или код.
6. Скопируйте отчёт, экспортируйте XLSX или отправьте результат в Jira.

Новый чек-лист получает случайный короткий `publicId` и URL вида:

```text
/report/851a9bd2
```

### Открыть конкретный чек-лист

Перейдите по URL:

```text
https://qa-report.company.ru/report/851a9bd2
```

Если ID найден в локальном кэше или, при включённом облаке, в серверной истории текущего пространства,
приложение откроет нужный чек-лист. Если ID неизвестен, будет показано понятное
сообщение с возможностью создать новый чек-лист.

Старый формат `/#/checklists/<id>` поддерживается как fallback.

### Использовать историю

В модалке "История отчётов" можно:

- искать отчёты;
- видеть количество всех, облачных и локальных записей;
- видеть короткий public ID экземпляра;
- отличать облачную и локальную запись по иконке;
- открыть сохранённую версию;
- создать копию;
- удалить запись;
- оставить комментарий к конкретному экземпляру.

Комментарий хранится отдельно от содержимого чек-листа и не влияет на `contentHash`,
поэтому сам по себе не вызывает конфликт версий.

### Разрулить конфликт

Если облачное хранилище включено и облачная версия изменилась, под хедером появляется уведомление
"Есть изменения в облаке" с кнопкой "Сравнить".

В модалке сравнения можно:

- открыть облачную версию;
- оставить локальную и явно перезаписать облако;
- сохранить обе версии.

При сохранении обеих версий исходная облачная запись остаётся канонической и
сохраняет старый `publicId`. Локальная расходящаяся версия сохраняется как новая
копия с новым `publicId`; если пользователь выбирает открыть её, URL сразу
переключается на новый `/report/<id>`.

## Импорт Чек-листов

### Ручной импорт Jira Wiki Markup

В меню Jira есть пункт "Загрузить из Jira".

Поддерживается:

- вставка Jira Wiki Markup напрямую;
- несколько таблиц в одном комментарии;
- разделы `h2.` / `h3.`;
- разные наборы колонок в разных таблицах;
- Jira-цвета статусов;
- встроенное форматирование, ссылки с вложенными или экранированными квадратными скобками и цвета в hex-формате или стандартных именах Jira;
- кодовые блоки Jira;
- изображения по имени вложения, если они приходят из Jira-комментария вместе со списком вложений.

### Импорт по ссылке на комментарий Jira

Можно вставить прямую ссылку на Jira-комментарий. Приложение:

1. использует текущие настройки Jira;
2. читает комментарий через Jira REST API;
3. подтягивает список вложений задачи, если хватает прав;
4. парсит Wiki Markup для Jira Data Center / Server или ADF для Jira Cloud;
5. создаёт чек-лист в текущем браузере.

### Входящий импорт из QA Assistant

QA Assistant может отправить чек-лист в QA Report через API:

```bash
curl -X POST http://localhost:4173/api/checklists/import \
  -H 'Content-Type: application/json' \
  -d '{
    "source": "qa-assistant",
    "format": "jira",
    "title": "Экспорт транзакций в Excel",
    "issueKey": "https://company.atlassian.net/browse/ADVINTAUT2-117",
    "content": "||Номер||Проверка||Как проверить||Ожидаемый результат||Фактический результат||Статус||Комментарий||\n|1.|Отображение кнопки Export|Авторизоваться как Admin|Кнопка Export видна и доступна для нажатия| | | |"
  }'
```

Поля:

| Поле | Обязательное | Описание |
| --- | --- | --- |
| `format` | да | Пока поддерживается только `jira` |
| `content` | да | Jira Wiki Markup таблицы или чек-листа |
| `source` | нет | Источник, например `qa-assistant` |
| `title` | нет | Название импортируемого чек-листа или первого раздела |
| `issueKey` | нет | Для текущего сценария сюда передаётся полная ссылка на Jira-задачу |

Несмотря на имя `issueKey`, для входящего импорта поле используется как ссылка на
задачу. Передавайте полный URL:

```text
https://company.atlassian.net/browse/ADVINTAUT2-117
```

Успешный ответ:

```json
{
  "ok": true,
  "checklistId": "ec8d6464-70e0-4c84-ba6e-31fbd7fd1c9f",
  "publicId": "851a9bd2",
  "url": "https://qa-report.company.ru/report/851a9bd2?importToken=ec8d6464-70e0-4c84-ba6e-31fbd7fd1c9f",
  "expiresAt": 1783285561851,
  "parsed": {
    "sections": 1,
    "rows": 15
  }
}
```

Дальше нужно открыть `url` в браузере. По этой ссылке QA Report заберёт payload
с сервера, создаст новый чек-лист и очистит `importToken` из адресной строки.

Публичный origin для `url` берётся из `QA_REPORT_PUBLIC_URL`, `APP_PUBLIC_URL`
или `PUBLIC_URL`, если переменная задана. Если переменной нет, сервер использует
`Forwarded` или `X-Forwarded-Proto` + `X-Forwarded-Host`; без них будет использован
обычный `Host` запроса, например `localhost:4173` при локальном вызове.

Ошибки:

| Код | Когда возвращается |
| --- | --- |
| `400` | `format` не равен `jira` |
| `400` | `content` пустой или не строка |
| `422` | Jira-разметку не удалось распарсить в пункты чек-листа |
| `404` | import token не найден или истёк |

Payload входящего импорта хранится во временной памяти Node-процесса 15 минут.
Jira-разметка не передаётся через query string; в URL находится только короткий
import token.

## Интеграция С Jira

В интерфейсе есть настройки Jira и действие "Отправить в Jira".

### Поддерживаемые варианты

| Jira | Формат комментария | Авторизация |
| --- | --- | --- |
| Jira Data Center / Server | Jira Wiki Markup | Personal Access Token, Basic Auth или Cookie |
| Jira Cloud | Atlassian Document Format | Email Atlassian + API token |

Адрес Jira, тип Jira и пользователь сохраняются локально в браузере. Токен или
пароль не пишутся в `localStorage` и живут только в памяти открытой вкладки.

### Публикация комментария

При публикации приложение:

1. берёт полную ссылку из поля "Ссылка на задачу";
2. извлекает ключ задачи из URL;
3. готовит комментарий в нужном формате;
4. загружает локальные вложения в Jira;
5. создаёт комментарий;
6. проверяет, что комментарий создан и читается обратно.

Если Jira или промежуточный proxy возвращает успешный HTTP-статус без объекта
комментария, приложение пытается найти созданный комментарий среди последних
комментариев задачи. При ошибке показываются диагностические детали: upstream
HTTP-статус, `Location`, краткое тело ответа, количество комментариев до и после
публикации и ошибки контрольного чтения.

### Вложения

Для Jira Data Center / Server:

- приложение читает существующие вложения задачи;
- выбирает свободное имя `screenshot-N.png`;
- вставляет изображения в комментарий как `!screenshot-N.png|thumbnail!`;
- если список вложений недоступен, к имени добавляется временная метка.

Для Jira Cloud:

- вложения публикуются как кликабельные attachment-card;
- код публикуется как ADF `codeBlock`;
- встроенное thumbnail-превью через Media Services UUID не используется.

Перед отправкой приложение проверяет сигнатуру изображения, MIME-тип и расширение.
Файлы загружаются по одному, чтобы проще диагностировать ошибку конкретного вложения.

### WAF / SSO / Browser Challenge

Если корпоративный WAF или SSO возвращает HTML browser challenge вместо JSON Jira
REST API, приложение останавливает публикацию до POST и возвращает
`JIRA_SECURITY_CHALLENGE`.

Для серверной интеграции администратору нужно разрешить исходящий IP приложения
либо исключить `/rest/api/*` из интерактивной browser-проверки при наличии
корректного `Authorization` header.

Cookie браузерной Jira-сессии приложение не копирует и не сохраняет.

## Обратная Связь

Кнопка с иконкой жука открывает форму обратной связи.

Форма:

- сохраняет обращение на сервере в `feedback-data`;
- сохраняет описание и техническую информацию в `feedback.json`;
- сохраняет приложенные скриншоты отдельными файлами;
- может приложить текущий чек-лист, только если пользователь явно включил галочку;
- не передаёт настройки Jira, пароль или токен.

В Docker каталог `feedback-data` подключён как volume `feedback_data`, поэтому
обращения не исчезают при пересборке контейнера.

### Email Через Resend

Feedback можно дополнительно отправлять на email через Resend.

API key хранится как Docker secret:

```bash
mkdir -p secrets
chmod 700 secrets
printf '%s' 're_...' > secrets/resend_api_key
chmod 600 secrets/resend_api_key
```

Адреса задаются через `.env`:

```env
FEEDBACK_TO_EMAIL=you@example.com
FEEDBACK_FROM_EMAIL=QA Report <feedback@your-domain.ru>
```

`FEEDBACK_FROM_EMAIL` требует подтверждённого домена в Resend. Если отправка email
не настроена, обращение всё равно сохраняется локально на сервере.

## Хранение Данных

| Данные | Где хранятся |
| --- | --- |
| Текущий черновик | `localStorage` браузера |
| Локальный кэш истории | IndexedDB браузера |
| Серверная история отчётов | SQLite-файл `reports-data/qa-report.sqlite`, используется только если пользователь включил облачное хранилище |
| Public ID экземпляра | SQLite и локальный кэш |
| Комментарий истории | SQLite для облачных записей, IndexedDB для локальных |
| Настройки Jira без секрета | `localStorage` браузера |
| Jira token / пароль | Только память открытой вкладки |
| Feedback | Серверный каталог `feedback-data` |
| Входящий импорт QA Assistant | Память Node-процесса, 15 минут |

По умолчанию чек-листы сохраняются только локально в браузере. Если пользователь
включил "Сохранять чек-листы в облачном хранилище", серверная история хранит
текстовую версию документа чек-листа как JSON в
`document_json`. По умолчанию embedded изображения, file-card и `data:`-payload
не отправляются и не сохраняются в SQLite, чтобы большие отчёты не перегружали
Node-сервер, reverse proxy и базу. Полная версия с вложениями остаётся в локальном
кэше браузера и используется для локального редактирования и публикации в Jira.

Метаданные вынесены в отдельные колонки: название, ссылка на Jira-задачу, ключ
задачи, окружение, общий статус, даты, владелец, `public_id`, `content_hash`,
`history_comment` и `deleted_at`.

Старые записи без `public_id` получают его при миграции или первом чтении.

## Защита От Конфликтов

В интерфейсе используются два понятия:

- локальная версия - копия чек-листа в текущем браузере;
- облачная версия - копия чек-листа в серверной истории SQLite.

При сохранении фронтенд отправляет последний известный `contentHash`. Если
облачная версия уже изменилась и hash не совпадает с базовым hash клиента,
backend возвращает `409 Conflict` и не перезаписывает документ.

`contentHash` считается по нормализованному содержимому чек-листа. В него не входят:

- `updatedAt`;
- `revision`;
- `lastSavedBy`;
- `lastSavedClientId`;
- UI-состояние фокуса, скролла и выбранной ячейки;
- комментарий записи в истории.

Такой механизм защищает от сценария, когда один и тот же отчёт открыт на двух
компьютерах: старая вкладка не сможет молча затереть более новую облачную версию.

## Как Определяется Владелец Истории

QA Report не реализует собственные логины и пароли. Backend выбирает владельца
по доступному контексту:

| Приоритет | Источник | Как работает |
| --- | --- | --- |
| 1 | SSO headers | Если reverse proxy передал `X-Forwarded-Email`, `X-Auth-Request-Email`, `X-Forwarded-User`, `X-Auth-Request-User` или `Remote-User`, отчёты привязываются к корпоративной учётке |
| 2 | Ключ пространства | Если пользователь указал ключ в настройках истории, отчёты привязываются к этому ключу |
| 3 | `clientId` браузера | Если SSO и ключа нет, отчёты привязываются к автоматически созданному ID текущего браузера |
| 4 | Anonymous fallback | Если браузер не передал `clientId`, используется технический fallback по адресу клиента |

Ключ пространства нужен для личного сервера и простого переноса между компьютерами:
укажите одинаковый ключ в настройках истории на разных устройствах, и они увидят
одну серверную историю. Это не полноценная авторизация: кто знает ключ, тот
получает доступ к этому пространству.

В корпоративном контуре рекомендуемый вариант - ставить QA Report за SSO/reverse
proxy и передавать identity через заголовки. Приложение при этом не хранит пароли
пользователей.

| Переменная | Назначение |
| --- | --- |

должен быть не ниже `QA_REPORT_MAX_BODY_MB`. Для Nginx обычно нужен
`client_max_body_size 150m;` или больше для endpoint `/api/jira/attachments`.

## Локальный агент для Jira через VPN

Кнопка «Агент» в хедере открывает настройки подключения и инструкции со
скачиваемыми архивами для macOS, Windows и Linux. Все варианты используют одно
Node.js-ядро и требуют Node.js 18 или новее.

Сценарий версии `0.2.6`:

1. пользователь скачивает архив, подключает корпоративный VPN и запускает агент;
2. QA Report создаёт одноразовый 8-значный код сроком на 10 минут;
3. агент обменивает код на отдельный секрет устройства и сохраняет его локально;
4. Jira credential настраивается в терминале агента через PAT/basic или Copy as
   cURL из авторизованной Jira-сессии и остаётся на устройстве;
5. браузер видит состояние устройства и может проверить доступность Jira через
   DNS, сертификаты и VPN-маршруты этого компьютера;
6. публикация комментария и вложений ставится в ограниченную очередь, агент
   выполняет Jira REST-запрос локально и возвращает подтверждённый `commentId`.

Jira token, пароль и cookies не передаются серверу QA Report: в заданиях находятся
только адрес Jira, готовый комментарий и явно выбранные вложения. Агент не является
универсальным HTTP proxy. Привязки устройств и задания хранятся в общей SQLite-базе
QA Report; секрет устройства в базе хранится только в виде hash. Локальный
credential агента пока защищён файловыми правами профиля пользователя; для
production-дистрибутива его нужно перенести в Keychain/Credential Manager/libsecret.

API локального агента:

| Метод | Путь | Назначение |

| `POST` | `/api/agent/pairings` | Создать одноразовый код текущего браузера/пространства |
| `POST` | `/api/agent/pair` | Сопрячь устройство и получить его секрет |
| `GET` | `/api/agent/status` | Получить состояние устройств текущего владельца |
| `POST` | `/api/agent/jobs` | Создать разрешённое задание для активного устройства |
| `GET` | `/api/agent/jobs/:id` | Получить состояние и результат задания |
| `POST` | `/api/agent/poll` | Получить следующее задание по ключу устройства |

## Известные Ограничения

- Входящий импорт из QA Assistant хранится временно и пропадает после истечения TTL
  или перезапуска Node-процесса.
- Серверная история по умолчанию хранит только текстовую версию отчёта: изображения
  и file-card остаются локально в браузере и не подтягиваются из облачной истории.
- Ключ пространства не является строгой авторизацией. Для корпоративной приватности
  нужен SSO/reverse proxy, который передаёт user identity в заголовках.
- SQLite рассчитан на один сервер/контейнер. Для горизонтального масштабирования
  нужен переход на PostgreSQL или другое внешнее хранилище.
- Jira Cloud не получает встроенное thumbnail-превью через Media Services, только
  кликабельные attachment-card.
- Итоговое отображение Jira Wiki Markup зависит от конкретной версии и настроек
  Jira Data Center / Server.
- Корпоративные WAF/SSO могут блокировать серверные Jira REST-запросы.
- Токены Jira не сохраняются между перезагрузками вкладки.

### Отбор при отправке в Jira

Окно «Что отправить в Jira» открывается для любого количества разделов.

История релизов находится в `release-notes.js`: новые записи добавляются в начало
массива с номером версии, датой ISO и списками `new`, `improvements`, `fixes`.

не показываются. Первая запись раскрыта, предыдущие версии свёрнуты.
Просмотр хранится в `qa-report-release-seen-v1` в localStorage; новый номер
версии снова включает индикатор. Отчёты и их содержимое не изменяются.

## Установка приложения и автономный запуск (PWA)

QA Report можно установить из адресной строки или меню Chrome/Edge. Когда браузер
предлагает установку, в шапке редактора также появляется кнопка «Установить QA Report».
Расположение и доступность команды зависят от браузера; в Safari используйте
доступную команду добавления сайта в Dock / на экран «Домой».
Требуется HTTPS; для локальной проверки подходят `http://localhost:4173` и
`http://127.0.0.1:4173`. Обычный HTTP по IP сервера для PWA не подходит.

При первом посещении Service Worker сохраняет полный интерфейс редактора.
Дождитесь его загрузки с работающим сервером перед автономной работой.
После этого приложение открывается без сервера, в том числе по ссылкам
`/report/<publicId>`, и использует существующие локальные данные браузера.
Установка не скачивает автоматически всю серверную историю или внешние вложения.
Доступны только ранее сохранённые на этом устройстве данные; текущий лимит
локальной истории — 50 записей. Очистка данных сайта удаляет локальные чек-листы
и автономный кэш. Установленное приложение не является резервной копией.

Облачное хранение сохраняет прежнее поведение и требует доступного сервера.
В этой первой версии PWA нет устойчивой очереди повторной отправки изменений:
автоматическая синхронизация всех правок после сбоя не гарантируется.
Jira, локальный агент и внешние хранилища по-прежнему требуют своих сетевых сервисов.
API, токены, вложения и загрузки не помещаются в кэш Service Worker.

При выпуске изменений HTML/CSS/JS/иконок обязательно увеличивайте `CACHE_NAME`
в `sw.js` и обновляйте список `SHELL`, если изменились URL ресурсов.
Обновление устанавливается только после загрузки всех ресурсов. Рядом с «Что нового»
появляется кнопка «Обновить»: она сохраняет чек-лист в IndexedDB, активирует
новую версию и перезагружает окно. При ошибке сохранения, открытом диалоге,
публикации или обработке вложений переключение блокируется с пояснением.
Другие окна и вкладки QA Report нужно закрыть перед нажатием кнопки.
Без нажатия кнопки новая версия ждёт закрытия всех окон приложения.
Проверка выполняется при запуске, возврате в окно, восстановлении связи и
каждые 15 минут в видимом окне (не чаще раза в минуту).
Для получения самой кнопки пользователям предыдущей версии нужно один раз
обновить страницу, затем закрыть все окна и вкладки приложения и открыть снова. `sw.js` и манифест сервер отдаёт с `no-cache`.

Проверка перед публикацией: открыть приложение по HTTPS/localhost, дождаться
активного Service Worker, создать локальный чек-лист, закрыть приложение,
остановить сервер и снова открыть приложение и ссылку на чек-лист.
Проверить редактирование, сохранение и повторное открытие без сети.

Цвет верхней панели установленной PWA следует теме устройства: светлый
`#f6f7fb` или тёмный `#1f2329`, через `theme-color` с `prefers-color-scheme`.
Тема редактора по-прежнему выбирается отдельно. Отрисовкой системной рамки
управляет браузер/ОС; сайт задаёт рекомендуемый цвет панели приложения.

### Компактное обновление в хедере

При готовности новой версии появляется кнопка с круговыми стрелками и цветной точкой. Подсказка при наведении объясняет действие; нажатие сохраняет чек-лист и запускает штатное обновление. На узких экранах подписи действий заменяются иконками, а панель действий при необходимости прокручивается горизонтально, не перекрывая Jira.
